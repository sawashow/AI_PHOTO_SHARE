# データベース設計

SQLite に保存するデータの形です。機能の範囲は [requirements.md](requirements.md)、画面は [screen-design.md](screen-design.md)、URL は [routing-design.md](routing-design.md) に従います。

テーブルはユーザーと投稿の 2 つです。写真の中身はデータベースに入れません。ファイルは `uploads/posts/` に置き、データベースには保存したファイル名だけを書きます。いいねとコメントのテーブルは作りません。

## テーブル一覧

| テーブル | 役割 |
|---|---|
| user | 登録した人。ログインと、投稿の投稿者表示に使う |
| post | 写真 1 枚の投稿。一覧と詳細に出す |

Peewee のモデル名は `User` と `Post` にします。SQLite 上のテーブル名は、Peewee の標準どおり小文字の `user` と `post` になります。

## なぜこの 2 つか

登録する人と、その人が出した写真は、別のまとまりです。人の情報を投稿のたびにコピーすると、同じ人の名前をあとから一箇所で扱えません。投稿の数だけ行が増えても、人は 1 行のままにするために、テーブルを分けます。

1 人は複数の投稿を持てます。投稿は必ず 1 人の投稿者を持ちます。この関係は、投稿側にユーザー番号を持たせて表します。ユーザー側に投稿番号の一覧は持ちません。

いいねは今回作らないので、「誰がどの投稿にいいねしたか」を保存するテーブルは不要です。コメントも今回の画面とルートに含めないので、コメント用のテーブルも作りません。

画像そのものをデータベースに入れないのは、写真の分だけ SQLite のファイルが大きくなるためです。一覧で写真を見せるときも、データベースから画像データを読む必要がありません。投稿を削除するときは、`post` の行を消してから、同じファイル名の写真を `uploads/posts/` から消します。

## user

登録した人を 1 行で表します。ログインはユーザー名とパスワードで行い、メールアドレスではログインしません。メールアドレスは登録時に保存するだけで、一覧や詳細には出しません。

パスワードはハッシュだけを保存します。入力されたパスワードそのものは列にしません。

| カラム | SQLite の型 | Peewee | 空 | 制約 | 内容 |
|---|---|---|---|---|---|
| id | INTEGER | モデルが自動で持つ主キー | 不可 | 主キー | ユーザー番号。自動で増える |
| username | TEXT | CharField | 不可 | | 登録時に入力されたユーザー名。画面に出す |
| username_normalized | TEXT | CharField | 不可 | ユニーク | ユーザー名を小文字にしたもの。重複判定専用 |
| email | TEXT | CharField | 不可 | | 登録時に入力されたメールアドレス |
| email_normalized | TEXT | CharField | 不可 | ユニーク | メールアドレスを小文字にしたもの。重複判定専用 |
| password_hash | TEXT | CharField | 不可 | | パスワードのハッシュ |
| created_at | TEXT | DateTimeField | 不可 | | 登録日時 |

`username` と `email` の文字数の上限は、列ではユーザー名 50 文字、メールアドレス 254 文字にしておきます。要件が決めているのは「空は登録しない」ことだけなので、長すぎる値を列の段階で受け付けないための上限です。

`username_normalized` と `email_normalized` を別列にする理由は、あとのユニーク制約で説明します。

## post

写真 1 枚の投稿を 1 行で表します。一覧は `created_at` の新しい順に、このテーブルの行を並べます。詳細は `id` が URL の `/posts/<id>` と一致する 1 行です。

| カラム | SQLite の型 | Peewee | 空 | 制約 | 内容 |
|---|---|---|---|---|---|
| id | INTEGER | モデルが自動で持つ主キー | 不可 | 主キー | 投稿番号。自動で増える |
| user | INTEGER | ForeignKeyField | 不可 | 外部キー | 投稿者。`user.id` を指す。列名は `user_id` |
| image_filename | TEXT | CharField | 不可 | ユニーク | `uploads/posts/` に保存したファイル名 |
| caption | TEXT | CharField | 不可 | | キャプション。空文字は許す。最大 200 文字 |
| created_at | TEXT | DateTimeField | 不可 | | 投稿日時。キャプションを直しても変えない |

`caption` は NULL にしません。未入力のときは空文字です。200 文字を超える値は、保存する前にアプリが拒否します。

`image_filename` には、アプリが付けた UUID などの名前だけを入れます。利用者が付けたファイル名、画像のバイナリ、画像の種類を表す別列は持ちません。種類と大きさは、保存する前にアプリが確認します。

## 主キー

- `user.id`
- `post.id`

どちらも整数で、新しい行を入れるたびに SQLite が番号を付けます。投稿詳細の URL は `post.id` を使います。

## 外部キー

| 子テーブル | カラム | 参照先 | 関係 |
|---|---|---|---|
| post | user_id | user.id | 投稿は 1 人のユーザーに属する。1 人のユーザーは複数の投稿を持てる |

投稿者のいない投稿は作れません。`user_id` には、実在する `user.id` だけを入れます。

ユーザーを削除する機能はありません。外部キーの削除時動作は `RESTRICT` にします。開発中にユーザーの行を消そうとしても、投稿が残っていればデータベースが拒否します。`CASCADE` にするとユーザー行と一緒に投稿行も消え、`uploads/posts/` の写真ファイルだけ残ります。

## ユニーク制約

| 対象 | 制約 | 理由 |
|---|---|---|
| user.username_normalized | ユニーク | `alice` と `Alice` を同じ名前とみなす |
| user.email_normalized | ユニーク | 同じメールアドレスは 1 人だけ |
| post.image_filename | ユニーク | 1 つの写真ファイルを、複数の投稿から指さない |

ユーザー名とメールアドレスは、画面に出す値とは別に、小文字へそろえた列で重複を禁止します。SQLite のユニーク制約は大文字と小文字を別の値として扱うため、`username` 自身にユニーク制約を付けても `alice` と `Alice` の両方を保存できてしまいます。

登録時は次を守ります。

- ユーザー名、メールアドレス、パスワードが空なら保存しない。
- 保存する前に、小文字へそろえたユーザー名とメールアドレスを作り、その値を正規化列へ入れる。
- すでに同じ正規化列があれば保存しない。アプリの確認と同時に、ユニーク制約でも拒否する。

ログイン時は、入力されたユーザー名を小文字へそろえ、`username_normalized` でユーザーを探します。登録時の大文字と小文字が違っていてもログインできます。

## インデックス候補

主キーとユニーク制約には、SQLite がインデックスを作ります。次はそれ以外で、あると一覧と詳細が楽になる候補です。友人同士の件数なら、最初から無くても動きます。

| 候補 | 理由 |
|---|---|
| post.created_at | 一覧を新しい順に並べる |
| post.user_id | 投稿者のユーザー名を一覧と詳細で一緒に読む |

`post.user_id` は外部キーですが、SQLite は外部キー用のインデックスを自動では作りません。投稿者を表示するたびにユーザー表を引くので、候補にしています。

## Peewee で実装する場合の注意点

- モデルは `User` と `Post` の 2 つだけにします。いいね用、コメント用のモデルは足しません。画像用の `BlobField` も使いません。
- `Post` の投稿者は `ForeignKeyField(User, backref="posts", on_delete="RESTRICT")` にします。フィールド名を `user` にすると、列名は `user_id` になります。`user.posts` で、その人の投稿をたどれます。
- SQLite は、最初の状態では外部キーを検査しません。接続したときに `PRAGMA foreign_keys = ON` を実行します。これを忘れると、存在しない `user_id` でも投稿を保存できてしまいます。
- `DateTimeField` の初期値には、現在時刻を返す関数を渡します。`datetime.now()` のように関数をその場で呼んでしまうと、アプリを起動した時刻がすべての行に入ります。
- パスワードは Werkzeug のハッシュを `password_hash` に入れます。比較もハッシュ用の関数で行い、平文と比べません。
- ユーザー名とメールアドレスの重複は、保存前の検索だけに頼らず、正規化列のユニーク制約で受けます。制約違反が起きたときは、成功扱いにせず、登録画面に理由を出します。
- キャプションの 200 文字、PNG・JPEG・GIF だけ、5MB まで、という制限はデータベースの型では表現しきれません。保存する前にアプリが検証し、無効なら `post` へ挿入しません。
- 投稿削除は、`post` の行を削除してから `image_filename` のファイルを消します。行の削除に失敗したら、ファイルは残したまま失敗を返します。ファイル削除に失敗したら、その失敗を記録し、成功として一覧へ進みません。
- テーブル作成は Peewee の `create_tables` で行います。SQLite ファイルと `uploads/posts/` は Git に含めません。
